# 서버화 설계 (Azure SQL + Vercel)

현재: 전체 데이터(`data` 객체)를 브라우저 localStorage에 저장, 로그인 없음.
목표: 전표·거래 데이터를 Azure SQL에 저장하고, 로그인(ID/비밀번호)과 역할별 접근권한을 서버에서 강제한다.
결정 사항: 다중 조직(중앙/본부/지부) · 4단계 역할 · 관리자가 계정 발급 · 기존 데이터는 백업 JSON 업로드로 이전.

## 1. 구조

```
브라우저(index.html, React)
   │  HTTPS, 쿠키 세션
   ▼
Vercel 서버리스 함수 (/api/*)   ← 권한 검사·입력 검증·감사로그는 전부 여기서
   │  mssql (매개변수화 쿼리만 사용)
   ▼
Azure SQL Database (khnp-accounting)
```

- 화면(index.html)은 누구나 받을 수 있는 정적 파일이다. 데이터는 로그인한 API 응답으로만 내려간다.
- 권한은 화면 숨김이 아니라 **서버가 매 요청마다 검사**한다. 화면 조작·개발자도구로는 우회되지 않는다.
- 조직 구분(`org_id`)은 항상 세션에서 가져온다. 클라이언트가 보낸 org_id는 쓰지 않는다 → 다른 조직 데이터 접근 불가.

## 2. 역할과 권한

| 기능 | super | admin | accountant | approver | viewer |
|---|:-:|:-:|:-:|:-:|:-:|
| 조직 생성, 조직 관리자 발급 | O | | | | |
| 사용자 발급·비활성·비밀번호 초기화(자기 조직) | | O | | | |
| 조직 설정·결재선·예산·연도마감 | | O | | | |
| 전표 작성·수정·삭제(임시/반려 상태만) | | O | O | | |
| 결재 상신 | | O | O | | |
| 결재 승인/반려 | | | | O(본인 단계만) | |
| 비품·계약 등록/수정 | | O | O | | |
| 조회(전표·장부·재무제표) | | O | O | O | O |

규칙(서버 강제):
- **결재자 단계 연결**: approver 계정은 `approval_step`(예: 사무장)을 가진다. 결재선 순서대로, 본인 단계가 차례일 때만 승인할 수 있다.
- **기안자 ≠ 결재자**: 본인이 작성한 전표는 본인이 승인할 수 없다.
- **승인된 전표는 수정·삭제 불가.** 정정은 역분개 전표로 한다(admin의 승인 취소는 감사로그에 사유와 함께 기록).
- super는 조직 데이터를 볼 수 없다(조직 생성·관리자 발급 전용). 최초 super 계정은 1회용 부트스트랩 토큰으로 만든다.

## 3. 로그인·보안

- 비밀번호: 서버에서 scrypt(솔트 포함)로 해시 저장. 최소 10자. 관리자 발급 임시 비밀번호는 첫 로그인 때 변경 강제.
- 5회 연속 실패 시 15분 잠금. 성공·실패 모두 감사로그.
- 세션: 무작위 토큰을 `HttpOnly; Secure; SameSite=Strict` 쿠키로 발급, DB에는 SHA-256 해시만 저장(8시간, 서버에서 즉시 폐기 가능). 브라우저 JS는 토큰을 읽을 수 없다.
- CSRF: SameSite=Strict + 쓰기 요청은 `Content-Type: application/json` 필수.
- SQL 주입: 모든 쿼리는 매개변수화. 문자열 이어붙이기 금지.
- XSS: React 자동 이스케이프 유지, `dangerouslySetInnerHTML` 미사용 확인.
- DB 접속 계정은 관리자가 아닌 최소 권한 `app_user`, 감사로그는 수정·삭제 금지.
- 비밀값(DB 비밀번호 등)은 Vercel 환경변수에만 둔다. 코드·채팅·깃허브에 두지 않는다.

## 4. 데이터 동기화 방식 (기존 화면 최대한 유지)

- 로그인 직후 `GET /api/data` → 기존 `data`와 같은 모양으로 조립해서 내려준다. 화면 코드는 대부분 그대로 쓴다.
- 쓰기는 localStorage 통째 저장 대신 항목별 API로 한다. 서버가 저장 후 최신 항목을 돌려주고 화면 상태에 반영한다.
  - `POST/PUT/DELETE /api/vouchers`, `POST /api/vouchers/:id/submit|approve|reject`
  - `PUT /api/budgets/:fy`, `POST /api/records/:kind`(비품·계약·예산변경), `POST /api/year-close`(한 트랜잭션)
- 동시 수정: 행마다 `version`을 두고 충돌 시 "다른 사람이 먼저 수정했습니다. 새로고침 후 다시 시도" 안내.
- 전표번호는 서버가 `doc_counters`로 채번(동시 입력해도 중복 없음).
- 다른 사용자 변경 반영: 창 포커스 시와 60초마다 재조회.
- 로컬 저장(오프라인) 모드는 제거하고, 기존 localStorage 데이터는 관리자가 백업 JSON 업로드로 서버에 이전(`POST /api/import`, admin 전용, 빈 조직에만 허용).

## 5. 환경/배포 주의

- Azure SQL 무료 서버리스는 유휴 시 일시중지된다. 첫 접속은 수십 초 걸릴 수 있어 API에서 재시도하고, 화면에 "데이터베이스를 깨우는 중" 안내를 띄운다.
- 방화벽: Vercel은 고정 IP가 없어 Azure SQL 서버 방화벽에서 외부 전체 허용이 필요하다. 그 대신 강한 비밀번호 + 최소 권한 계정 + 로그인 잠금으로 보완한다.
- **리전**: 현재 DB가 Australia East다. 한국 사용자가 쓰면 느리고, 조합원·재정 정보의 국외 보관(개인정보 국외 이전) 문제도 있다. **Korea Central로 다시 만들고 Vercel 함수 리전을 `icn1`(서울)로 맞추는 것을 권장**한다. DB가 비어 있는 지금이 가장 쉽다.
- 첨부파일(증빙)은 현재 EXE 전용이라 이번 범위에서 제외. 필요하면 Azure Blob Storage로 후속 설계.
- 메뉴 클릭 수(MongoDB)는 별개 기능이라 그대로 둔다.

## 6. 진행 단계

1. **DB 준비**: `db/schema.sql` 실행, `app_user` 생성, Vercel 환경변수 등록(`SQL_SERVER`, `SQL_DATABASE`, `SQL_USER`, `SQL_PASSWORD`, `BOOTSTRAP_TOKEN`).
2. **인증**: `/api/auth/*`(로그인·로그아웃·내 정보·비밀번호 변경), 부트스트랩, 로그인 화면.
3. **관리**: 조직/사용자 발급·비활성·초기화 화면(super, admin).
4. **데이터 API + 화면 연동**: 전표(결재 흐름 포함) → 예산 → 비품·계약 → 연도마감 → 가져오기.
5. **점검**: 권한 우회 시도(다른 조직 ID, 역할 외 API), 동시 수정, 감사로그, DB 일시중지 상황.

각 단계는 배포해서 동작을 확인한 뒤 다음으로 넘어간다.

## 7. 증빙 파일 (Azure Blob Storage) — 구현됨
- 비공개 컨테이너 `evidence`, 경로 `{조직ID}/{voucher|contract}/{대상ID}/{파일ID}.{확장자}` (원래 파일 이름은 전표/계약 JSON에만 기록).
- `api/files/[op].js`: 서버가 로그인·역할·조직을 확인하고 파일 한 개에만 유효한 임시 주소(SAS: 업로드 10분/다운로드 5분)를 발급 → 브라우저·앱이 Blob과 직접 주고받음(Vercel 요청 크기 제한 회피).
- 형식은 확장자 허용 목록(PDF·사진·한글·오피스)으로 서버가 MIME을 정하며, 20MB 제한. 승인/결재 중 전표의 증빙은 삭제 불가. 삭제된 파일은 7일간 복구 가능(소프트 삭제).
- 연결 문자열은 Vercel 환경변수 `AZURE_STORAGE_CONNECTION_STRING`/`AZURE_STORAGE_CONTAINER`에만 보관. 키 교체 시 두 곳(.env.local, Vercel)을 함께 갱신.
- 알려진 한계: 올린 뒤 전표를 저장하지 않고 닫으면 파일이 고아로 남는다(용량 미미). 필요하면 주기적 정리 작업을 추가한다.
